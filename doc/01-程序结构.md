## 三层职责边界

理解这个项目最关键的一件事：**代码分成三层，依赖是单向的**。

```
apps/web  ──依赖──▶  packages/shared  ◀──依赖──  apps/server
（只展示）            （纯函数，无 IO）            （有状态，有 IO）
```

### `packages/shared` —— 纯函数层

- **不允许**出现 `fs`、`fetch`、`Fastify`、`Vue` 任何一方的东西
- 只做「输入 → 输出」，随机性全部通过传入的 `rng` 函数
- 好处：后端算出来的结果，前端可以原样复用（比如编辑器里预览检定成功率）

### `apps/server` —— 有状态层

- 管数据库、文件、模型调用、并发锁
- `engine/resolver.ts` 是**单回合内**的纯逻辑（仍然是纯函数，只是放在服务端）
- `services/play.ts` 负责**编排**：把 resolver 的纯函数串成一条流水线

### `apps/web` —— 展示层

- **不包含任何规则判定**。前端不算成功率、不掷骰、不改状态
- 它收到的 `CheckResult`、`EventFireRecord` 都是后端算好直接渲染的

## 一回合推演的完整数据流

这是整个项目最核心的流程，改任何玩法都要先看懂它。入口在 `services/play.ts` 的 `runTurn()`。

```
用户点击「选项」/ 输入文字
   │
   ▼
POST /api/chat  （或 SSE）
   │
   ├─ [0] withLock(sessionId)   ← 同一世界线串行，防并发丢状态
   │
   ├─ [1] 剧本节点推进
   │       ├─ 已在节点里 → 只取选项，不重跑 on-enter（否则 san/hp 每回合叠加）
   │       ├─ 点了剧本选项 → applyChoice 推进
   │       └─ 模型给了 goto → enterNode
   │
   ├─ [2] 意图推断  parseIntent(content)
   │       └─ 关键词匹配 → 建议技能（只是建议，不替玩家决定）
   │
   ├─ [3] 事件判定
   │       ├─ enter_node（仅真正换节点时）
   │       ├─ turn_start
   │       └─ player_action
   │       每回合最多 2 个，按 priority 排序
   │
   ├─ [3.5] 理智检定（事件声明了 sanCheck 才跑）
   │
   ├─ [3.2] 剧情偏离计数 plotDrift
   │
   ├─ [4] 世界书扫描 scanWorldBook()
   │       └─ 关键词命中 + 条件 + 概率 + 冷却，产出 loreHits
   │
   ├─ [5] 检定
   │       ├─ intent=roll   → runCheck（玩家主动掷）
   │       ├─ intent=choice → 选项自带 check
   │       └─ 自由输入有风险 → 自动检定（世界关掉就不掷）
   │
   ├─ [6] before_narration / turn_end 事件
   │
   ├─ [7] 组装提示词 buildChatTurns()
   │       └─ 按真实 contextWindow 算预算，超了逐级瘦身
   │
   ├─ [8] 调用模型（流式）
   │       └─ SSE 逐 token 推送，同时累积原文
   │
   ├─ [9] 离线兜底（模型挂了也能推进剧本）
   │
   ├─ [10] 解析元数据 splitMeta()
   │       └─ 六层容错：标记 → 裸 JSON → 截断修复 → 行内选项 → 清思考标签 → 小模型兜底
   │
   ├─ [11] 合并模型给的状态变更
   │
   ├─ [12] 结局处理（首次到达才生成继承存档）
   │
   └─ [13] 落库
           ├─ messages      消息正文 + meta
           ├─ message_states ★ 完整状态快照（分叉/回退靠它）
           └─ sessions.state 当前状态
```

### 几个容易踩的设计点

**为什么每回合都存完整状态快照？**
分叉时要从「那一刻」继续，而不是拿父线当前状态近似。`message_states` 表就是干这个的。

**为什么种子是 `会话种子 + 回合数 × 7919`？**
不能用 `Date.now()`，否则同一存档点两次同样输入会掷出不同点数，分叉重演就复现不了。

**为什么 `enterNode` 有 `applyOnEnter` 开关？**
玩家待在节点里不动也算一回合。如果每回合都结算 `::: on-enter` 的 san/hp，坐着不动就会耗干血条。

## 数据库表

| 表 | 用途 |
|---|---|
| `c_worlds` / `c_characters` / `c_worldbooks` / `c_scripts` | 内容镜像（从文件扫描，可重建） |
| `sessions` | 世界线（含 `state_json`、`owner_id` 隔离） |
| `messages` | 消息正文 + `meta_json` |
| `message_states` | **每条助手消息的完整状态快照** |
| `legacies` | 结局时生成的继承存档 |
| `rooms` | 多人房间 |
| `settings` | 模型配置等键值对 |

**只有运行期数据（sessions / messages / legacies / rooms / settings）不可重建**，
`c_*` 四张表删了会从 `content/` 重新扫描生成。

## 并发与一致性

| 问题 | 解法 | 位置 |
|---|---|---|
| 同一世界线并发推演丢状态 | 按 `sessionId` 串行锁（promise 链） | `lib/session-lock.ts` |
| SSE 长连接没法整体加锁 | `acquire()` / `release()` 手动版 | 同上 |
| 分叉/回退状态错位 | 消息级状态快照 | `message_states` |
| 内容重扫时半空表 | 目前无事务保护（已知问题） | `content/store.ts` |
